**Product:** Banking Retention Intelligence Platform (v2.0.0 Enterprise)

### 1. Probability Calibration & Class Imbalance
**Q: What is probability calibration, and why were original scores uncalibrated?**  
**A:** Probability calibration ensures that if a model predicts a probability $p$, roughly $p \times 100\%$ of those instances genuinely belong to the positive class.  
In earlier versions, models were trained with `class_weight='balanced'`. Because churn prevalence in this dataset is only $16.4\%$, the artificial loss weighting shifted the decision threshold and severely inflated output scores (mean score $0.436$ vs. actual $0.164$). While this artificially boosted raw churn recall at a fixed $0.50$ threshold, the output values could not be interpreted as true probabilities or used in financial expected value formulas.

---

### 2. Platt Scaling & Brier Score
**Q: How was calibration achieved, and how do you evaluate it?**  
**A:** We trained the baseline pipeline without artificial class weighting and wrapped it in `CalibratedClassifierCV(method='sigmoid', cv=5)` using Platt Scaling (fitting a sigmoid link function $\sigma(A f(x) + B)$ on training cross-validation folds).  
Calibration quality is evaluated using the **Brier Score Loss** (mean squared difference between predicted probabilities and binary outcomes):
$$\text{Brier} = \frac{1}{N} \sum_{i=1}^N (p_i - y_i)^2$$
- Uncalibrated model: Brier score was **$0.2180$** (and uncalibrated mean score was $0.4360$).
- Calibrated production model: Brier score improved to **$0.1216$**, with a mean predicted probability of **$0.1685$** matching the true test holdout churn rate ($16.4\%$).

### 3. The 0.748 ROC-AUC Ceiling & Model Selection
**Q: Why does Logistic Regression outperform complex algorithms like XGBoost and Random Forest on this dataset?**  
**A:** Because the underlying customer dataset was synthetically generated via a linear logistic equation (`src/generate_sample_data.py`):
$$P(\text{Exited}=1) = \sigma\left(\beta_0 + \sum_{j} \beta_j X_j + \epsilon\right)$$
Because the ground truth log-odds are strictly linear in the features with additive Gaussian noise $\epsilon \sim \mathcal{N}(0, \sigma^2)$, the Bayes-optimal decision boundary is a hyperplane.  
The theoretical discrimination ceiling for this synthetic noise level is **$\text{ROC-AUC} \approx 0.748$**.  
Complex non-linear algorithms like Random Forest ($0.7188$ AUC) and XGBoost ($0.7102$ AUC) overfit the synthetic variance, while Calibrated Logistic Regression achieves **$0.7295$ ROC-AUC**, hitting the practical optimum. Further hyperparameter tuning is mathematically futile.

### 4. Preventing Data Leakage
**Q: How did you ensure zero data leakage between training, validation, and holdout test splits?**  
**A:**  
1. **Split First:** The $10,000$ raw records were partitioned into an $80\%$ training split ($N=8,000$) and a $20\%$ holdout test split ($N=2,000$, `data/processed/test_split.csv`) using stratified sampling on `Exited`.
2. **Encapsulated Preprocessing:** Standard scaling and one-hot encoding parameters were fitted exclusively inside an `sklearn.pipeline.Pipeline` on training data.
3. **Internal Calibration Folds:** `CalibratedClassifierCV` performed 5-fold cross-validation strictly within the $8,000$ training rows.
4. **Untouched Test Split:** The test split was scored once and never used for model selection, feature pruning, or threshold tuning.

### 5. Out-of-Fold (OOF) Scoring vs. In-Sample Leakage
**Q: Why does `powerbi_dataset.csv` and the dashboard use out-of-fold scoring instead of full-dataset model inference?**  
**A:** In the original project, `powerbi_dataset.csv` ran `model.predict_proba()` across all 10,000 rows including the training data. This created in-sample optimistic bias: training instances had artificially confident predictions.  
We replaced this with **5-fold out-of-fold (OOF) cross-validated scoring** for training rows combined with holdout scoring for test rows (`ScoreSource: out_of_fold | test`). Every single probability in `data/processed/scored_customers.csv` was generated by a model that did not see that row during fitting.

### 6. Causal Retention vs. Churn Prediction
**Q: Why is a high churn prediction score NOT a retention decision?**  
**A:** Churn prediction only estimates $P(\text{Churn} \mid X)$ (the risk of leaving). It does not tell you $P(\text{Churn} \mid X, \text{do}(\text{Action}))$. In retention marketing, customers fall into four causal quadrants:
1. **Lost Causes:** Customers who will churn regardless of intervention (high risk, zero uplift). Contacting them wastes budget.
2. **Sure Things:** Customers who stay regardless of contact (low risk, zero uplift). Contacting them is an unnecessary cost.
3. **Sleeping Dogs:** Customers who stay if left alone, but churn if contacted (negative uplift, e.g. reminding dormant users of subscription fees).
4. **Persuadables:** Customers who stay *only* if they receive an intervention (positive uplift $\Delta \tau > 0$).  
Targeting the highest churn risk ranks Lost Causes and Sleeping Dogs. Prescriptive retention requires targeting **Persuadables**.

### 7. Uplift Simulator Design & Limitations
**Q: How does the Uplift Simulator work, and what are its limits?**  
**A:** Because the original dataset lacked treatment/control intervention data from randomized trials, we built a synthetic response engine (`dashboard/core/uplift_simulator.py`).  
It assigns heterogeneous treatment responses based on customer attributes:
- Dormant accounts contacted by high-touch service calls show high positive retention uplift ($\tau \approx +0.22$).
- Highly sensitive, low-balance accounts receiving promotional fee waivers show modest uplift ($\tau \approx +0.12$).
- Certain cohorts with high fees experience negative uplift ($\tau \approx -0.05$, Sleeping Dogs).  
**Limitation:** It is a synthetic simulation designed for pedagogical and architectural demonstration. In production, uplift models (T-Learner, X-Learner, Causal Forests) must be trained on genuine randomized control trial (A/B) data.

### 8. Constrained Decision Optimization (MILP)
**Q: What is the mathematical optimization problem solved by the Decision Engine?**  
**A:** The engine maximizes Expected Net Benefit subject to campaign budget and operational capacities:
$$\max_{x_{i,k}} \sum_{i=1}^N \sum_{k=1}^K x_{i,k} \left( \hat{\tau}_{i,k} \cdot \text{CLV}_i - c_k \right)$$
Subject to:
1. **Exclusivity:** $\sum_{k=1}^K x_{i,k} \le 1, \quad \forall i \in \{1,\dots,N\}$ (at most one action per customer).
2. **Budget Constraint:** $\sum_{i=1}^N \sum_{k=1}^K x_{i,k} c_k \le B$ (total campaign budget).
3. **Capacity Constraints:** $\sum_{i=1}^N x_{i,k} \le C_k, \quad \forall k \in \{1,\dots,K\}$ (e.g. max 50 service call slots).  
We solve this using Mixed Integer Linear Programming (MILP) via `scipy.optimize.milp` with a branch-and-bound simplex solver.

### 9. Policy Comparison Advantage (+61.5% Net Benefit)
**Q: What is the empirical performance advantage of MILP prescriptive targeting over churn risk ranking?**  
**A:** Under an identical €10,000 campaign budget on held-out customers:
- **Policy A (Churn Risk Ranking):** Contacts customers with the highest predicted $P(\text{Churn})$. Net benefit is **€24,650** because budget is consumed by expensive Lost Causes who churn anyway.
- **Policy B (MILP Causal Targeting):** Targets customers with highest net benefit $\tau_{i,k} \text{CLV}_i - c_k$ within capacity limits. Net benefit is **€39,820**.  
This yields a **+61.5% net benefit lift**, demonstrating why prescriptive optimization is economically superior.

### 10. Customer Lifetime Value (CLV) Financial Proxy
**Q: How is Customer Lifetime Value calculated, and why is it labelled an assumption-based estimate?**  
**A:** Retail banks earn net interest margin (NIM) on deposits and transaction fees, offset by servicing costs. We implement an annualized discounted cash-flow model:
$$\text{CLV}_i = \left[ \sum_{t=1}^{H} \frac{\text{Balance}_i \times \text{NIM} + \text{Fee} - \text{Servicing}}{(1 + r)^t} \right] \times (1 - p_i)$$
Parameters (configurable in UI):
- $\text{NIM} = 3.0\%$ (annual deposit margin)
- $\text{Fee} = \text{€}50$ (annual fee income)
- $\text{Servicing} = \text{€}40$ (maintenance cost)
- $H = 3\text{ years}$ (planning horizon)
- $r = 8.0\%$ (discount rate / cost of capital)  
It is explicitly labelled an assumption-based proxy because it models forward-looking earning capacity rather than historical accounting records.

### 11. Explainable AI: SHAP Methodology
**Q: How does Explainable AI work on this platform?**  
**A:** We use Shapley additive explanations (SHAP) from cooperative game theory:
$$f(x) = \phi_0 + \sum_{j=1}^M \phi_j(x)$$
- $\phi_0$ is the base value (expected log-odds over training data).
- $\phi_j(x)$ is the marginal attribution of feature $j$ to the prediction.  
We extract model weights and use `shap.LinearExplainer` (or `shap.TreeExplainer` for trees). The UI renders local waterfall plots showing how age, balance, or complaints push individual risk up or down from the portfolio average.

### 12. Counterfactual Recommendations
**Q: How are actionable counterfactuals computed?**  
**A:** For a customer classified as High Risk ($p \ge 0.50$), counterfactual search finds the minimal adjustment in actionable features (e.g. enrolling in online banking, acquiring a second product, or resolving complaints) required to reduce $p < 0.20$ (Low Risk).  
**Governance Constraint:** Protected demographic attributes (`Age`, `Gender`, `Geography`) are held strictly invariant during counterfactual optimization.

### 13. Algorithmic Fairness Metrics
**Q: Which fairness metrics are audited, and what do they mean?**  
**A:** Using Fairlearn's `MetricFrame`:
1. **Demographic Parity Difference:** The maximum difference in selection rate (rate of being targeted for retention intervention) between demographic groups:
   $$\text{DPD} = \max_{g} P(\hat{Y}=1 \mid A=g) - \min_{g} P(\hat{Y}=1 \mid A=g)$$
2. **Equalised Odds Difference:** The maximum disparity in True Positive Rate (TPR) or False Positive Rate (FPR):
   $$\text{EOD} = \max\left( \max_{g}\text{TPR}_g - \min_{g}\text{TPR}_g, \max_{g}\text{FPR}_g - \min_{g}\text{FPR}_g \right)$$
Tolerance threshold: Configurable at $\le 0.10$.

### 14. Fairness Bootstrap Confidence Intervals
**Q: Why use bootstrap resampling for fairness, and how was it optimized?**  
**A:** Point estimates of fairness metrics can fluctuate due to small group sample sizes. We generate empirical $95\%$ confidence intervals via 500 bootstrap iterations ($2.5\text{th}$ and $97.5\text{th}$ percentiles).  
**Optimization:** Rather than calling Fairlearn's groupby 500 times (which took $35\text{ seconds}$), we implemented vectorized numpy calculations over group boolean masks, reducing runtime to **$0.31\text{ seconds}$ (over 100x speedup)** while generating identical percentiles.

### 15. The Proxy Variable Trap
**Q: Why does dropping protected attributes (`Gender`, `Geography`) fail to guarantee fairness?**  
**A:** Removing a column from model training does not eliminate group disparities because non-protected variables often act as proxies.  
For example, in Germany, customers in this dataset have higher average account balances and higher baseline churn rates. Even if `Geography` is dropped, `Balance` and `LoanAmount` partially reconstruct the geographic signal. The platform includes a live side-by-side retraining panel demonstrating that dropping `Gender` and `Geography` reduces ROC-AUC to $0.7075$ without eliminating proxy bias.

---

### 16. Small Group Sample Size Warnings
**Q: Why does the fairness audit warn about sample sizes $< 50$?**  
**A:** In holdout splits, subgroups with fewer than 50 observations (e.g. customers aged $60+$ with $N=29$) have high statistical variance. High disparities in small groups may represent sampling noise rather than systematic algorithmic discrimination.

### 17. Real-Time Streaming Risk Architecture
**Q: How does the real-time streaming pipeline function?**  
**A:**  
- **PySpark Structured Streaming (`spark/spark_streaming_risk.py`):** Ingests JSON event files from `data/streaming/events_in/` using an event-time watermark of 10 minutes and sliding/tumbling windows of 15 minutes. It aggregates rolling transactions, complaints, and balance drawdowns, and scores customer churn risk.
- **Pure-Python Micro-Batch Fallback (`src/streaming/microbatch_runner.py`):** A lightweight runner that executes identically in resource-constrained or local environments without requiring an active Spark cluster. It processes batches in $\approx 48\text{ ms}$ ($4,000+\text{ events/sec}$).

### 18. Population Stability Index (PSI) & Drift
**Q: How is model drift detected in production?**  
**A:** We use the Population Stability Index (PSI) to compare reference baseline distributions ($P$) against live streaming batches ($Q$):
$$\text{PSI} = \sum_{b=1}^{B} (Q_b - P_b) \times \ln\left(\frac{Q_b}{P_b}\right)$$
- $\text{PSI} < 0.10$: Stable / No significant drift.
- $0.10 \le \text{PSI} < 0.25$: Moderate drift; monitoring advised.
- $\text{PSI} \ge 0.25$: Significant distribution shift; model retraining required.

### 20. What Would Change with Real Banking Data?
**Q: If you replaced this synthetic dataset with real retail banking data, what would change?**  
**A:**  
1. **Model Non-Linearity:** Real customer interactions contain complex multi-way feature interactions (credit-line utilization x life stage x macroeconomic rate hikes); gradient-boosted trees (XGBoost/LightGBM) would likely outperform linear models.
2. **Temporal Stationarity:** Real customer data exhibits macro seasonality and interest-rate regime shifts, requiring rolling-window time-series validation rather than static k-fold CV.
3. **Causal Experiments:** We would have genuine historical randomized control trial (A/B testing) logs with treatment and control assignments, enabling true causal uplift modeling.
4. **Volume & Partitioning:** Data volumes would expand from megabytes to terabytes, requiring multi-node Spark clusters with partitioning on `date` and `customer_id`.

### 21. FastAPI v2 Security Architecture
**Q: How does the FastAPI service defend against security threats?**  
**A:**  
- **Probe Protection:** Schema validation via Pydantic v2 rejects absurd values (CreditScore outside $300-850$, Age $<18$, negative balances) with structured HTTP 422 JSON errors.
- **Upload Denial-of-Service Defense:** Limits batch CSV uploads to $5,000$ rows and $5\text{ MB}$ payload size.
- **Zero Pickle Deserialization:** Uploads must be raw CSVs; pickle or joblib files from user requests are strictly rejected.
- **API Key Token Verification:** Production mode enforces the `X-API-Key` header; missing or invalid keys return HTTP 401.
- **Stack Trace Suppression:** Global exception middleware intercepts unexpected server errors, logging details internally while returning sanitized HTTP 500 JSON to clients.

### 22. Persistent Campaign State Machine
**Q: How does the campaign management system prevent operational errors?**  
**A:** Built on SQLAlchemy 2.x ORM with SQLite default and PostgreSQL support.  
It enforces a strict lifecycle state machine:
$$\text{draft} \longrightarrow \text{approved} \longrightarrow \text{in\_flight} \longrightarrow \text{completed} \text{ or } \text{cancelled}$$
- Targets cannot be imported into active campaigns.
- Campaigns cannot be launched without explicit pre-approval and budget validation.
- All actions record user, timestamp, old state, and new state in an immutable `audit_log` table.

### 24. Pure-Python PDF Generation Architecture
**Q: Why use ReportLab instead of headless browser tools like WeasyPrint or wkhtmltopdf?**  
**A:** Tools like WeasyPrint require heavy system C-libraries (Pango, Cairo, GObject) or full headless Chrome binaries that fail or cause memory overhead in containerized environments.  
`reportlab==5.1.0` is a pure-Python document engine that generates high-fidelity, deterministic PDF byte streams directly in memory in $<150\text{ ms}$ with zero external runtime dependencies.
